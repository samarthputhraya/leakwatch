### D-001 · 2026-11-18 · Run everything inside WSL2 Ubuntu 26.04
- **Decision:** All build, data and service commands run in WSL2 (`Ubuntu`, kernel 2, systemd enabled). Windows-side Python 3.12 and Java 25 are not used.
- **Reason:** PRD §0 ("If the OS is Windows, use WSL2"). Spark, Kafka and Docker are far less painful on Linux.
- **Alternatives:** native Windows (needs winutils for Spark, Docker Desktop with admin rights) — rejected.

### D-002 · 2026-11-18 · Source in the OneDrive workspace, venv and data on the WSL disk
- **Decision:** The git repo is the VS Code workspace folder (`…/OneDrive/Documents/mega project`, seen from WSL as `/mnt/c/...`). The Python venv lives at `/root/.venvs/leakwatch` (`UV_PROJECT_ENVIRONMENT`) and data lives at `/root/leakwatch-data` (`LEAKWATCH_DATA_DIR` in `.env`). If `LEAKWATCH_DATA_DIR` is unset, code falls back to `<repo>/data/` (gitignored) as the PRD layout says.
- **Reason:** (1) the team edits in VS Code on Windows, so source must stay visible there; (2) a 100M-reading Parquet lake and a venv with tens of thousands of files must not be synced by OneDrive; (3) file I/O across the `/mnt/c` 9P bridge is several times slower than the WSL ext4 disk, which matters for Spark and Parquet.
- **Risks:** the repo path contains a space (`mega project`) — the Makefile uses only relative paths and quotes; data paths have no spaces. OneDrive can briefly lock files during sync; if git ever reports lock errors, pause OneDrive sync or move the repo to WSL (`~/leakwatch`) and open it with VS Code Remote-WSL.
- **Alternatives:** whole repo in WSL (`~/leakwatch`) + VS Code Remote-WSL — the best-performing option and a good later move; not chosen now because the team's workspace is already the OneDrive folder.

- **Problem:** PySpark 3.5.9 (`ml`, `mllib`, `sql` extras) requires `numpy<2`. WNTR ≥ 1.4.0 requires `numpy>=2.2.6`. pyarrow 26 refuses numpy 1.x at import time (not declared in its metadata). Spark's Python workers will run the simulator (`mapPartitions`), so both must live in one environment.

- **Alternatives:** Spark 4.x (supports numpy 2) — rejected because the PRD fixes Spark 3.5.x; separate venvs for simulation and Spark — rejected (Spark workers need the simulator in-process).
- **Revisit if:** PySpark's Arrow path fails with pyarrow 25 in Phase 1 → downgrade pyarrow (no other package constrains it now).

### D-007 · 2026-11-18 · Scaling data from epyt-flow; GNN training scenarios from WNTR
- **Measured** (`reports/metrics/sim_benchmark.json` at commit 22ba83c; one 15 mm abrupt leak on p461, 5-minute steps, one process each): WNTR WNTRSimulator (PDD, split-pipe leak) ran 48 h in 22.3 s and 7 days in 74.0 s (3,077–3,243 equivalent readings/s, peak 410–756 MB). epyt-flow (EPANET) ran 48 h in 15.1 s and 7 days in 51.4 s (4,535–4,666 readings/s, peak 262–358 MB). "Equivalent readings" = time steps × 119 BattLeDIM sensors. An earlier run of the same code on the same machine measured epyt-flow at 13.0 s / 45.4 s, so expect ±15% run-to-run variance; the ranking was the same both times.
- **Decision:** bulk simulation for the 100M-reading scaling story (Phase 4) uses **epyt-flow**; single-leak scenarios for GNN training (Phase 5) use **WNTR** as PRD §4.2 describes (PDD, leak on a junction inserted mid-pipe).
- **Reason:** epyt-flow is ~1.4–1.7× faster and uses about half the memory per worker. With WSL capped at 7 GB, memory per Spark worker limits parallelism more than CPU does (18 logical cores). Projected single-core time for 100M readings: ~6.0 h (epyt-flow) vs ~8.6 h (WNTR); both divide by the number of parallel workers.
- **Sanity check:** WNTR's 15 mm leak reached 15.1 m³/h, consistent with the benchmark's own leaks (p461: 21.3 mm, peak 30.5 m³/h; outflow scales with diameter²).
- **Note:** neither engine is "too slow" outright; the choice is about memory headroom. Revisit in Phase 4 with the real Spark `mapPartitions` throughput.

### D-010 · 2026-11-18 · K-Means "normal" = background leakage allowed; strict leak-free run as ablation (confirmed by the team)
- **Problem:** PRD §7.3 trains K-Means on 2018 windows that overlap no known leak. Measured (`data_summary.json`): only 2.2% of 2018 steps (2,310, about 8 days in early January) have no leak flowing; 2019 has none (mean 10.3 leaks flowing at once).
- **Decision (confirmed by the user on 2026-11-18):** the main BDT model treats small, long-running leaks as background leakage, as utilities do, and excludes from training only windows near leak onsets and during abrupt leaks (exact exclusion rule set and logged in Phase 3). A second model trained on the strict ~8 leak-free days is reported alongside as an ablation.
- **Impact:** the BDT report must state how "normal" was defined and show both results.

### D-011 · 2026-11-18 · Raw lake = readings as received; stateful cleaning moves to the cleaned layer (Phase 2)
- **Decision:** the Phase 1 stream parses, validates (contract), deduplicates and *flags* out-of-range values, then writes `lake/raw`. Forward-filling gaps of ≤ 2 steps and stuck-sensor flags (PRD §7.2) are applied when building the cleaned/feature layer in Phase 2, using `leakwatch.data.quality` as the reference implementation and the batch/stream parity test.
- **Reason:** forward-filling creates readings that never arrived and stuck flags depend on per-sensor history across micro-batches; neither belongs in a "raw" layer, and both need the same state handling as the windowed features. Keeping raw = as received also makes the lake auditable against the source (contract tests compare every value).
- **Also:** messages that break the `scada.readings` contract are not dropped silently; they go to `lake/_rejects/raw`.

### D-012 · 2026-11-18 · Kafka: `apache/kafka:4.3.2`, single KRaft node, no volume, `restart: unless-stopped`
- **Image:** the official Apache image (no Bitnami/Confluent licensing or availability changes). 4.3.2 is the latest patch of the previous minor line (4.4.0 was 4 weeks old). Spark's connector ships kafka-clients 3.4.x, which Kafka 4.x brokers accept (they require clients ≥ 2.1).
- **No volume:** the image runs as a non-root user and a named volume would need ownership fixes; more importantly Kafka is only the transport — the lake is the source of truth. `make down` drops queued messages; `make lake-reset` rebuilds consistently.
- **Restart policy:** WSL stops the distro (and Docker with it) when no Windows-launched process is attached — observed during development: Kafka exited with 143 between two `wsl` calls. `restart: unless-stopped` brings the same container (and its messages) back when the distro restarts. Running commands from an open WSL terminal avoids the stop entirely.

### D-013 · 2026-11-18 · Exactly-once into the lake: watermark dedup + `foreachBatch` commit protocol
- **Dedup:** `withWatermark("ts", "1 hour").dropDuplicatesWithinWatermark(source, scenario_id, sensor_type, sensor_id, ts)`. The producer is idempotent, so Kafka itself holds no retry duplicates; dedup covers a publisher that re-sends recent data (e.g. a restarted replayer). Data older than the watermark is dropped as late and counted (`late_rows_dropped_by_watermark`). Consequence: the stream must see event time move forward — replaying an *older* year into the same checkpoint drops it as late. Rebuild with `make lake-reset` instead.
- **Sink:** Spark's `foreachBatch` is at-least-once. Each micro-batch is staged, then its files are moved into the lake with a `b<batch_id>-` prefix, and a commit marker is written last; a re-run of a committed batch is skipped, and a re-run of a half-moved batch first deletes its old files (`stream/lake_writer.py`). Verified by unit tests and an end-to-end test with an injected duplicate, a late copy and a malformed message.
- **Alternatives:** Spark's file sink is exactly-once but hides committed files behind `_spark_metadata`, which DuckDB does not read — readers could see files from failed batches.

### D-015 · 2026-11-18 · Exact rule for "normal" timestamps (baselines now, K-Means training in Phase 3)
- **Principle (D-010, user-confirmed):** small long-running leaks are background leakage and count as normal; time near leak onsets and during abrupt leaks does not.
- **Rule (per leak in the ground truth, `leakwatch.features.normal`):**
  - *background leak* = incipient **and** peak outflow ≤ `normal.background_max_peak_m3h` (10 m³/h): only its onset `[start, start + 7 days]` is excluded (`onset_exclusion_days`, = the 7-day detection horizon of PRD §7.4), capped at its repair;
  - every other leak (*significant*: abrupt, or peak > 10 m³/h, or peak unknown) is excluded from start to repair, or to the end of the data if never repaired;
  - a timestamp is normal iff it is in none of these intervals (bounds inclusive). A 1 h window is normal iff all its steps are (Phase 3).
- **Why 10 m³/h:** 2018 peak outflows split cleanly: 5.11, 5.49, 6.87, 6.91 m³/h (p427, p654, p257, p810 — exactly the four leaks never repaired, which carry into 2019) and then 16.21 … 35.38 m³/h. Any threshold in (6.91, 16.21) gives the same 2018 result. Abrupt leaks are always significant, also the three small abrupt 2019 leaks (5.3–5.6 m³/h).
- **Effect:** measured in `reports/metrics/baselines_hour_of_week.json` (normal days, stretches). The strict rule (every leak excluded while active, the D-010 ablation) is the same function with `rule="strict"`.
- **Known limitation:** the excluded periods are uneven over the year (all of February, March, July and August, and May to mid-June, are excluded; 151.68 normal days in `baselines_hour_of_week.json`), so hour-of-week baselines lean on spring/autumn/winter demand. Hour-of-week medians ignore season by design (PRD §7.2).

### D-016 · 2026-11-18 · Cleaning semantics: causal stuck flag, interior forward fill, per-type exemptions
- **Stuck:** a reading is flagged once it and the previous 11 steps (`stuck_min_steps` = 12) were all *observed* with the same value. Causal (the first 11 steps of a run are not flagged, because a streaming job cannot know yet that the run will get long), a missing step breaks a run, filled readings are never flagged. Reference: `data.quality.stuck_flags`; the Spark version is tested against it.
- **Exempt types:** `cleaning.stuck_exempt_types: [flow, level, amr]`. Measured in Phase 0: PUMP_1 sits at exactly 0 or 44.07 m³/h for up to 233 steps (pump state), tank T1 holds its level for up to 83 steps (0.01 m rounding), AMR n25 repeats one value for up to 109 steps. For these types a constant value is normal operation, so the flag would be almost always wrong. Pressure keeps the rule; the PRV-regulated n215 (area B) will be flagged often, which is accurate (Finding 3).
- **Forward fill:** only *interior* gaps of 1–2 missing steps are filled (`filled = true`), once the reading after the gap has arrived. The pandas reference also fills a short gap at the very end of a frame; a stream cannot know a trailing gap is short, so we do not (the only difference, documented in `features.clean`).
- **Out of range:** flags from Phase 1 are carried; flagged values are left out of feature statistics and AMR sums (`features.exclude_out_of_range: true`). No BattLeDIM reading is out of range.
- Flags are data-quality columns, not model inputs. Each feature row carries counts (`n_filled`, `n_stuck`, `n_out_of_range`, `n_series_missing`) for Phase 3 alert explanations.

### D-017 · 2026-11-18 · Cleaned layer, baselines and feature-table layout
- **`lake/clean`** (not listed in PRD §6.2): cleaned readings with `filled`/`stuck` flags, same partitions as `lake/raw`, built in batch by `make features`. It feeds the baselines and makes the flags queryable (DuckDB view `clean_readings`). Layer sizes: `reports/metrics/lake_layers_summary.json`.
- **Series:** one per pressure/flow/level sensor (37) plus the summed AMR consumption per area (PRD §7.2). All 82 AMRs are in area C, so there is one AMR series, `amr_sum__C` (L/h): 38 series.
- **Baselines** (`lake/baselines/hour_of_week`): exact median (`F.median`) per series and hour of week (0 = Monday 00:00 UTC) over the normal 2018 timestamps of D-015. 38 × 168 rows.
- **Statistics per series and window:** mean, population std, min, max, least-squares slope against time (units per hour), mean residual (value − baseline). 38 × 6 = 228 feature columns named `<series>__<stat>` (`pressure__n54__slope`), plus window keys and quality counts. One wide row per window (the "pivot" of PRD §7.2), built with conditional aggregation so the column set and order are fixed by `FeatureSpec` even when a series is missing.
- **Windows:** `F.window` 1 h, sliding 15 min, aligned to the epoch. A window belongs to the date/year of its start. The batch job keeps only windows fully covered by data: 35,040 for 2018 (the last three use 2019 readings) and 35,037 for 2019 (its last three would need 2020) — `features_battledim_<year>.json`.
- **Same function:** `features.windows.window_features(readings, baselines, spec)` (cleaning included) is what the batch job applies to raw lake rows and what the streaming job applies to each micro-batch plus carried history. Batch reads the raw layer (not `lake/clean`) so both paths make literally the same call.

### D-018 · 2026-11-18 · Streaming features: foreachBatch with carried history, separate live table
- **Problem:** cleaning and 1 h windows need readings from earlier micro-batches. Spark's own stateful operators could do the windows, but not the forward fill or the stuck rule without a second, different implementation (`applyInPandasWithState`) — the opposite of batch/stream parity. Streaming `pivot` is also unsupported.
- **Decision:** the stream (Kafka → the raw ingest's parse + watermark dedup) hands each micro-batch to `stream.features_stream.FeatureBatchWriter`, which unions it with a carried *tail* (readings from `next window start − 55 min`: 11 steps of stuck history ≥ 3 steps of fill history), calls the batch function, and emits each window once, in order, as soon as data `features.stream.lateness_minutes` (15) past its last step has arrived. 15 min ≥ (2-step gap + closing reading), so the stream never misses a fill the batch makes. Feature files, tail and state are committed together with the lake_writer protocol (D-013): a retried batch restarts from the previous committed state.
- **Output:** `lake/features_stream/` with the batch schema, kept apart from `lake/features` so the training/evaluation tables stay immutable while the live path runs (online vs offline store). `make features-parity` compares the two window by window.
- **Consequences:** a window is available ~15 simulated minutes after it ends (2.5 s at the 360× demo speed); readings older than the next window to emit are counted as late and ignored. Event time is global across sources/scenarios, like the raw watermark (D-013); Phase 7's simulated leaks must keep event time moving forward.
- **Numerical fix found by the full-year parity run (2026-11-18):** the first run (`reports/metrics/features_parity_battledim_run1_epoch_time.json`, code 5a5afce) matched all 70,076 windows, but 1,539 of 16.3 M cells differed beyond rtol 1e-9, all in `amr_sum__C__slope` (max |diff| 3.4e-6). The slope used hours since the epoch (~4.3e5) as time; Spark's covariance then loses ~1e-10 of each time step, and the large AMR sum (~3e4 L/h) turns that into ~1e-6 slope noise that depends on aggregation order. Time is now measured from each window's start (0 … 11/12 h); a unit test checks the slope against numpy to 1e-9 on large values at 2029 timestamps.

### D-020 · 2026-11-19 · K-Means detector: training split, threshold, persistence, labels, variants
- **Pipeline (Spark MLlib, PRD §7.3):** VectorAssembler → StandardScaler (mean 0, std 1) → PCA (fewest components for `pca_variance`) → KMeans, k in 2..20 chosen at the elbow of the SSE curve (kneedle point); the silhouette (ClusteringEvaluator) of every k is reported. Fitted parameters are exported and applied by a numpy scorer (`bdt.scorer`), tested equal to Spark's `transform` (same cluster, distance equal to 1e-9), so batch evaluation and the live stream score with one code path.
- **Training data:** 2018 windows that are normal under D-015 (every step), split by whole UTC days in a 5-day cycle: 3 train days, 1 threshold day (τ = p99 of its scores), 1 validation day (persistence). Overlapping windows are never split at random.
- **Alert rule:** m consecutive windows above τ; m = smallest candidate with ≤ 2 false alarms/week on the validation days (2018 only). An alert's `start_ts` is the end of its m-th window (the moment it can be raised); it closes after 4 windows below τ. Explanation: each series' share of the squared distance (PCA difference mapped back to the standardized features); area = top series' area. Estimated loss = mean excess inflow (p227 + p235 residuals), floored at 0, labelled an estimate.
- **Labels (PRD §7.4):** tp = alert starts within [start, start + 7 d] of a leak that started in the year; preexisting = otherwise, while only leaks from earlier years are active (tracked apart); fp = the rest. Because 2019 always has many leaks flowing, the evaluation also reports the **chance level** (detection rate of the same number of alerts placed at random) and an **onset contrast** (score 24 h after vs before each leak start), which do not depend on the alert rate.
- **Variants** (all trained on 2018 only): `kmeans` = all 228 PRD features (the BDT deliverable); `kmeans_strict` = trained on the ~8 strictly leak-free days (D-010 ablation); `kmeans_delta` = week-over-week change features (experiment); `kmeans_residual` = only the 38 residual features, PCA 99%. The residual variant is the **live model** because 2018 validation leak onsets (excluded from training) rise above τ more often: 5 of 6 abrupt onsets vs 4 of 6, and 40% of leak windows above τ vs 23.5% (scikit-learn exploration on 2018 only). Results: `bdt_kmeans_train.json`, `bdt_kmeans_2019.json`.
- **Finding:** with absolute features, 95% of the variance is the daily demand cycle (8 PCA components) and leak signatures sit in the dropped directions; in 2019 the share of windows above τ grows from 5% (January) to ~100% (December) as leaks accumulate, so every variant's 7-day detection rate is at chance level. Reported as is.

### D-022 · 2026-11-19 · Live scoring inside the feature stream
- `bdt.live.LiveScoring` runs in the feature stream's `foreachBatch` (D-018): newly emitted windows are scored, the alert trackers (state per source/scenario) resume from the committed state, and score rows and alert versions are staged next to the feature files and committed together (`lake_writer.commit_batch_multi`); alert versions then go to Kafka `alerts` (at least once; consumers key on `alert_id` + `version`). The rows are tiny, so the driver writes them with pyarrow instead of starting two more Spark jobs per batch.
- Verified: a 12 h 2019 replay at 360× raised the same alert at the same event time as the batch evaluation (`bdt_live_replay_2019.json`).

### D-023 · 2026-11-19 · Scaling data: 313 seven-day epyt-flow scenarios, Spark-parallel, through Kafka
- 30-day scenarios needed ~1 GB per epyt-flow worker and thrashed this 7.6 GB WSL machine (workers crashed); 7-day scenarios use ~0.4 GB. 313 × 7 days × 288 × 119 = 75.1M readings, plus 25.0M BattLeDIM = 100.1M in the lake.
- Spark `mapPartitions` runs one scenario per task; Python workers are **not reused** (memory grew across scenarios), and each task runs EPANET in a private scratch directory (EPANET writes fixed-name temp files into the working directory; crashed runs had left ~1.8 GB in the repository).
- Scenarios follow each other in event time from 2020-01-06 (the raw watermark needs event time to move forward, D-013), each with ±10% demand-pattern noise, 0–2 random leaks, Gaussian sensor noise and 0.01 rounding; they reach `lake/raw` (source=sim) only through Kafka (PRD §5).

### D-024 · 2026-11-19 · GNN training data from EPANET emitter leaks; inputs = two hourly residuals
- Scenarios use WNTR's EpanetSimulator with an emitter at the leak junction (exponent 0.5, coefficient Cd·A·√(2g)): the same orifice law as WNTR's leak model, ~1 s per 2 h run instead of tens of seconds with WNTRSimulator, which makes the PRD's 5,000-scenario full scale feasible on a laptop.
- Train/serve consistency (PRD §8.2): residual = reading (+ sensor noise) − median of 5 noisy leak-free runs from the same time of day; inputs are each pressure sensor's mean residual in the first and second hour of the leak, i.e. the `residual` statistic of two consecutive 1 h feature windows. Live, the localizer reads exactly those two feature windows; for the 2019 benchmark it uses their week-over-week change (older leaks cancel out).

### D-029 · 2026-11-19 · GNN inputs: sensor closeness and a global sensor context
- The first GNN design followed PRD §8.2 literally: node features = the two residuals at the 33 sensor nodes (0 elsewhere), `is_sensor`, elevation, base demand; 3 message-passing layers. On the 5,000-scenario set it ranked the leak in its top 5 less often than the MLP (validation top-5 0.145 GCN, 0.144 GAT vs 0.271 MLP; the run's log, its results were lost to a later crash). Reason: with 3 layers a junction only hears sensors within 3 hops; most of L-Town's 782 junctions have none, so their scores depend on static features alone.
- Two additions, both standard: (1) a *positional encoding* per node, `exp(-pipe distance to sensor k / 500 m)` for each of the 33 sensors, so every junction is identifiable and "near which sensors" is explicit; (2) a *global sensor context*, an MLP embedding of all 66 residual values broadcast to every node before message passing (the MLP baseline's information, available to the GNN). Layers keep residual connections.
- Kept honest by an ablation in the same run (`dl.gnn.variants`): GCN and GAT with both additions, GCN without the context, without the closeness, and without both (the first design). The model used live is the one with the best validation top-5 among all variants including the MLP.
- Outcome (`dl_gnn.json`): test top-5 GAT 0.339, GCN 0.309, MLP 0.229, nearest sensor 0.190. Ablation (GCN): without the global context 0.102, without closeness 0.176, without both 0.097, so the first design's weakness was the missing view of distant sensors, not the graph layers. The PRD target (top-5 ≥ 60% on medium and large leaks) is missed: 40.2% for the GAT. GAT training took 4.2 h of the 5.1 h run on 12 CPU threads.
- `make gnn` writes its metrics before it updates the alerts, so a failure in the lake update can no longer lose a trained comparison (it did once: arrays read back from DuckDB were not converted to lists, fixed in `bdt.data.alerts_to_spark`).

### D-030 · 2026-11-19 · Live detector: K-Means combined index (PCA distance + reconstruction error)
- Found in the live demo: a simulated 30 mm leak at junction n300 (≈ 53 m³/h) raised the inflow residual from about 5 to 60 m³/h, yet the live model's score stayed near 2 (τ = 6.4). The score is the distance to the nearest centre *inside* the 6 kept PCA components; normal 2018 variation (demand cycles, background leakage) defines those components, and an inflow change without a matching pressure pattern lies almost entirely outside them (its squared reconstruction error went from ≈ 0.05 to ≈ 31). The PCA-space distance alone only sees leaks that also move the pressure sensors in a "normal-looking" direction.
- Fix, standard in PCA-based process monitoring (Hotelling T² + SPE, combined index): score = (d / d_ref)² + q / q_ref, with d the K-Means distance in PCA space, q the squared PCA reconstruction error of the standardized window, and d_ref, q_ref their p99 on normal 2018 threshold days. K-Means, k, the PCA and the alert procedure are unchanged; τ and m are re-derived on 2018 exactly as before. PRD §7.3 allows the distance "in the scaled/PCA space"; this is the full scaled-space deviation, each part weighed by its normal spread. Explanations add both parts per feature.
- Selection on 2018 only (2019 never used): `make bdt-synthetic` adds EPANET leak signatures (60 random junctions × 10/20/30 mm, 10 start times) to normal Nov–Dec 2018 windows. Combined index vs PCA distance on the same residual features: leaks detected 68.9% vs 48.3%, false alarms on the leak-free background 1.07 vs 1.21 per week, median time to detection 0.58 h vs 0.92 h (`bdt_synthetic_leaks.json`). The live model is now `kmeans_residual_ci`; the 2019 evaluation reports all five variants.
- Consequence on 2019 (reported, not tuned away): the more sensitive score is above τ in 85.7% of 2019 windows (residual: 76.6%), so alerts stay open across new leak onsets and fewer leaks get a *new* alert within 7 days: 7 of 19 (abrupt 4 of 9) at 1.40 false alarms/week, vs 14 of 19 (abrupt 8 of 9) at 2.38 for the PCA distance (`bdt_kmeans_2019.json`). Both are near the chance level of a year that is never leak-free. A deployed detector would re-baseline after repairs; this project keeps 2019 untouched for tuning.

### D-040 · 2026-11-21 · ST: property-based tests and mutation testing of the code behind the numbers
- Why: line coverage (70.9%) says a line ran, not that a test would notice a wrong result. Two additions measure that instead. **Property tests** (`hypothesis`, `tests/unit/test_properties.py`): invariants checked on generated inputs — the official score does not depend on submission order; its bookkeeping adds up (TP + FP + repeats = reports in the year; duplicating a submission doubles the false positives and never loses a true positive); pipe distances are symmetric; re-baselining ignores a constant offset and maps a constant series to 0; the SQL guard never passes a write statement, also behind a harmless `SELECT` in the same text; the number guardrail accepts every value it was given, rounded to 0–3 decimals. **Mutation testing** (`make mutation`, mutmut 3.8.1): the code is changed one small edit at a time (operator, constant, string, boundary, removed argument) and the hermetic unit tests are rerun; a change that no test notices ("survived") is a gap in the tests or dead code.
- Scope: the modules whose bugs would change a reported number or let an unsafe query through — `eval.battledim_score`, `eval.detection`, `features.rebaseline`, `bdt.alerts`, `copilot.sql_guard`, `copilot.guardrails` (`[tool.mutmut] only_mutate`). Spark, torch and simulator code is left out: one mutant would cost minutes. Tests run: `tests/unit` without the slow, Spark and data-dependent markers. Score = killed / (killed + survived); mutants in code no selected test reaches ("no tests", mostly CLI `main`s) and timeouts are reported separately. `st_mutation.json` lists every survivor.
- First run (code ff89a56, 4 workers, 64 min): 2,645 mutants, 1,829 killed, 486 survived, 31 timeouts, 299 without tests → **79.0%** (alerts 87.7%, scorer 85.0%, guardrails 75.6%, rebaseline 73.5%, detection 71.0%, SQL guard 68.5%).
- What the survivors showed, and what changed: untested paths (SQL guard: `FETCH FIRST`, a `LIMIT` exactly at the cap, catalog-qualified tables, the `limit_changed` flag, the error text that lists the views; rebaseline: the exact half-window threshold, the left-closed window, minute steps, a hole in the data; detection: inclusive window and period bounds, unsorted alerts, the per-leak rows, the chance level against its closed form 1 − (1 − 7/365)ⁿ, `onset_contrast` had no test at all), one bug (a repeated timestamp made the rebaseline step 0, so every reference was missing; the batch features have unique timestamps, so no reported number changes) and dead code (sqlglot keeps `FETCH` under `limit`, so the separate `fetch` branch never ran; removed). Many survivors are equivalent mutants (the alias of a wrapped subquery, the sort kind on unique timestamps, `copy=False` on a tree that is not reused) and are left.
- Second run with those tests (code fa0a731, fresh `mutants/`, 35 min): 2,735 mutants (the scorer grew with D-041), 2,181 killed, 296 survived, 0 timeouts, 258 without tests (the scorer's `main`) → **88.0%** (2,181 / 2,477 = 0.8805) (alerts 92.0%, rebaseline 90.3%, scorer 89.9%, guardrails 87.5%, detection 84.3%, SQL guard 83.1%).

### D-044 · 2026-11-21 · Localizer: GLS inversion against the sensitivity matrix; chosen on simulations and 2018
- **Final quality pass (owner request, 2026-11-21).** Every choice in D-044 … D-050 is made on simulations and 2018 only. 2019 has been looked at in earlier passes (D-037 … D-043 reported it every time), so any choice made now still carries some selection bias towards what worked on 2019 before; it is scored once more at the end, with the final configuration, whatever it gives.
- **PRD metric, reported as defined.** PRD §10: top-5 accuracy of the *exact* leak junction on held-out simulated *medium + large* leaks (diameter ≥ 10 mm), test split of `make gnn`. The earlier headline (GCN 0.307) was over all sizes; on medium + large the same GCN has 0.393 and the live network (`gcn_sens_no_context`) 0.304. Both numbers are now in `dl_localizer.json`, with within-300 m shares next to them.
- **Why the old cues fall short.** The noise of the simulated residuals (perturbed roughness, background leaks, demand draws, sensor noise) is strongly correlated across sensors: in the training residuals the largest eigenvector holds two thirds of the variance (`noise.sim.top_eigen_share`). A day with a little more demand lowers every pressure at once, so a plain cosine with the sensitivity signature (0.390) is pulled towards the wrong junctions.
- **Model-based inversion (`dl.inversion`).** For every junction, the best leak size `a ≥ 0` (a closed-form 1-D search) and the weighted error `(x − a s_j)ᵀ Σ⁻¹ (x − a s_j)`, `s_j` the cached sensitivity signature (15 mm EPANET leak, nominal model), Σ a noise covariance: `sim` = second moment of the training scenarios' residuals after their true leak's fit; `real` = second moment of the 2018 normal windows' re-baselined residuals (14,075 pairs of hourly windows, the localizer's own input). Ridge `λ·tr(Σ)/n·I` chosen on validation medium + large top-5 (grid 1e-4 … 0.3 → 1e-4).
- **Time-of-day templates were not built.** The planned bank (junction × start hour × size) was tested first on the existing matrix (averaged over 03:00 and 15:00 starts): GLS accuracy by start hour shows no peak at those two hours, so templates per hour would not help; the GLS step alone gives the gain.
- **Held-out simulations (667 test scenarios, 382 medium + large).** Medium + large top-5: GLS (sim) **0.694** (95% Wilson 0.646–0.738) · GLS (real noise) 0.633 · sensitivity cosine 0.390 · GCN (best network, `dl_gnn.json`) 0.393 · live network 0.304 · previous posterior 0.278 · nearest sensor 0.191 · interpolation 0.136. - **Fusion and a hybrid GNN, measured.** Rank fusion of GLS + network + sensor prior + interpolation: 0.345 / 0.369 (sim / real Σ); adding the network's log-probability to GLS lowers sims top-5 at every weight tried (0.70 → 0.58 at weight 2). A GCN trained to add a correction to the GLS log-likelihood (logits = GLS/T + w·GCN, w starting at 0, early stopping on validation) lowered validation top-5 from the first epoch (0.697 → 0.66 → 0.62); early stopping kept GLS alone. With 3,107 training scenarios for 782 junctions the network learns no useful correction.
- **Choice on simulations and 2018 (`make localizer`).** Seven candidates fixed in `dl.localizer_selection.candidates`. Three development measures: sims medium + large top-5, 2018 recorded leaks within 300 m (top-1, oracle time), 2018 official score of one report per 2018 batch alert at the top node. Rule: best mean rank (ties: the 2018 official score). Written after the 2018 numbers of the first dry run were seen: the official score alone (the D-041/D-042 rule) would pick `rank_all_sim` (€77,918) over `gls_sim` (€75,144), a difference smaller than one alert, while `rank_all_sim` is half as accurate on simulations (0.345 vs 0.694) and worse on the 2018 leaks (28.6% vs 35.7%); the owner's brief asks for weights chosen on held-out sims *and* 2018, so the official score became one vote of three.
